## Why the former percentage is suspended

The historically reported **90% comprehensive / 96% implementation-grade** values were planning judgments, not reproducible measurements. The only earlier explicit weighted rubric in `COMPREHENSIVE_ANALYSIS_LEDGER.md` has 14 weights totaling 100, but its displayed coverage values produce **55.59%** when multiplied by those weights, while the nearby prose calls it an 82% historical snapshot. That table may have been left stale while the prose advanced; it cannot independently verify the later estimates. The old figures are now superseded by the evidence-based **89% comprehensive / 94% readiness** scores; they were not replaced with 55.59%, zero, or a function-address ratio. Function/address completion remains separately uncalibrated.

The separate [function-denominator audit](research/checkpoints/ANALYSIS_CHECKPOINT_2026-09-24_FUNCTION_DENOMINATOR_AUDIT.md) found 93,287 non-`Unwind@` entries in Ghidra; the current validated registry contains 2,568 curated semantic addresses. Neither is a validated count of reachable application functions. The 345-row current-server packet-source map with zero documented reachable gaps measures **source-to-document inventory**, not runtime protocol interoperability, full handler semantics or whole-client completion. Block counts, UI RTTI-name counts and asset counts likewise must not be converted into a client percentage.

## Session accounting rule from here forward

Each block starts with one ID and the prior evidence; ends with **closed / narrowed / contradicted / unchanged**, a precise residual, and whether it passed an observable-contract exit test. Block count is activity, not progress. Whole-client score changes require a revised weighted row, evidence, exit test, arithmetic and sensitivity to uncertain scope. Report the current **89% comprehensive / 94% readiness** scores and function/address accounting separately; never turn the raw registry/export ratio into behavioral coverage.
