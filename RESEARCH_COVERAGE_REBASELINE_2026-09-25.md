# Stardust.exe research coverage: measurement reset

Date: 2026-09-25. Scope: verified original `C:\Stardust-DEV\Stardust.exe` (SHA-256 `E782BF1C49B3DA730F66B54BC558947C46493F7133F672EED1D8E0C56A6B6150`), configured original assets and current Stardust-3 source. This is an audit and work queue, **not** new client-function coverage. No build, engine decision or live client/server test is authorized by this document.

## Why the former percentage is suspended

The historically reported **90% comprehensive / 96% implementation-grade** values were planning judgments, not reproducible measurements. The only explicit weighted rubric in `COMPREHENSIVE_ANALYSIS_LEDGER.md` has 14 weights totaling 100, but its displayed coverage values produce **55.59%** when multiplied by those weights, while the nearby prose calls it an 82% historical snapshot. That table may have been left stale while the prose advanced; it cannot verify either 82% or today's 90%/96%. Later increases were not accompanied by a current per-workstream numerator, denominator and exit-test ledger. Therefore **no defensible current whole-client percentage can be quoted**. The old numbers are retained as historical estimates, not silently replaced with 55.59%: the table itself is dated/stale and 55.59% is its *arithmetic result*, not today's coverage.

The separate [function-denominator audit](research/checkpoints/ANALYSIS_CHECKPOINT_2026-09-24_FUNCTION_DENOMINATOR_AUDIT.md) found 93,287 non-`Unwind@` entries in Ghidra and 2,528 currently curated semantic addresses. Neither is a validated count of reachable application functions. The 345-row current-server packet-source map with zero documented reachable gaps measures **source-to-document inventory**, not runtime protocol interoperability, full handler semantics or whole-client completion. Block counts, UI RTTI-name counts and asset counts likewise must not be converted into a client percentage.

| Engine-decision research | Engine-neutral architecture and equal-spike criteria documented | Reachability/compatibility gates below; Godot versus DX12/Vulkan remains untested | All blocking original-asset and lifecycle questions bounded enough to specify fair spikes; user then explicitly authorizes the build/spikes |

These axes are not interchangeable. The user's stronger “entire client” request requires the function-level accounting axis in addition to an engine-decision-grade behavioral model. We should report both rather than call a behavior-focused percentage “100%.”

## Session accounting rule from here forward

Each block starts with one ID and the prior evidence; ends with **closed / narrowed / contradicted / unchanged**, a precise residual, and whether it changed a denominator or passed an exit test. Publish block count only as activity, never as percent progress. A new whole-client score, if still useful, requires a fresh table of weights, current workstream scores, evidence, exit tests, arithmetic and sensitivity to uncertain scopes. Until then the honest report is **percentage uncalibrated; substantial analysis complete, material gaps remain**.
