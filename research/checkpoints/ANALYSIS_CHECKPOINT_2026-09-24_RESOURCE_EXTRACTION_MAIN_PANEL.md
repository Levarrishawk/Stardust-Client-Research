# Analysis checkpoint — resource-extraction main panel to server commands

Question A09 / W10+W13; the existing [resource manager checkpoint](ANALYSIS_CHECKPOINT_2026-09-22_RESOURCE_MANAGER_HARVESTER.md) already closed `0xEA` pool snapshots and `0xED` hopper-empty correlation. This block adds the **previously unmapped main-panel buttons and synchronized-UI subscriptions**. Target is the verified original `Stardust.exe`, with current Stardust-3 source read-only for policy correlation.

MSVC RTTI `SwgCuiResourceExtraction` yields the main mediator vtable `0x015F1E20` and callback subobject `0x015F1D9C`. Constructor `0x00D7A630` binds `switchon`, `switchoff`, `buttonchangeresource`, `buttonaccesshopper`, `buttonok`, resource name/rate bars, capacity/health pies and diagnostics. Activation `0x00D7ABA0` checks the selected object as `InstallationObject`, requests the current resource-data snapshot, refreshes the local synchronized-UI view and installs typed subscriptions for Active, ExtractionRate/Max, ResourcePool(s), Hopper/Max, Condition, readiness, and `CuiResourceManager::PoolsChanged`. Deactivation `0x00D7B0C0` removes these subscriptions and restores UI/input state. Presentation callbacks read `ClientInstallationSynchronizedUi` rather than deserializing network bytes directly.

Button dispatch `0x00D7B400` is pointer-identity based. Power On and Off call `0x00D7C0A0` with `1` and `0` respectively. That routine suppresses a redundant local state request and, when authoritative prerequisites are present, calls `0x0070AFA0`. The latter selects the exact strings `harvesterActivate` / `harvesterDeactivate`, resolves their command CRC, and uses `0x0046E5F0` -> `client_command_queue_enqueue_VA_0046D7A0` with the selected installation as target. The synchronized-UI Active event refreshes the panel; clicking does not itself make the server state authoritative. The resource-change button calls `0x0070B1E0`, which similarly enqueues `harvesterGetResourceData`, then opens `WS_ResourceExtraction_SetResource`. Hopper opens `WS_ResourceExtraction_Hopper`; OK hides the mediator. The resource-manager `0xEA` response and `0xED` empty/discard transaction remain as previously documented, not new discoveries here.

Current server command registrations are in `CommandConfigManager2.cpp` lines ~720–723. `HarvesterActivateCommand` and `HarvesterDeactivateCommand` require command-state/locomotion validity, a harvester or generator target, 20-metre range, admin rights, and the appropriate current active state before setting `InstallationObject::active` under its lock. `HarvesterGetResourceDataCommand` checks player/installation/zone and sends `HarvesterResourceDataMessage` (`0xEA` via player controller); the inspected handler does not perform the power-command admin/range checks, so the three policies should not be conflated.

The precise local validation in `0x00D7C0A0` beyond the visible selected-object/pointer checks, SetResource submission, and panel readiness failure handling remain for later bounded blocks. No whole-client percentage change.
