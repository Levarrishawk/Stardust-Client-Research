# Analysis checkpoint — SKTM bind-pose transform route

Target: verified `C:\Stardust-DEV\Stardust.exe`; reconstructed Ghidra pseudocode and direct x86 call order. This follows the deployed SKTM disk-layout and corpus-invariant checkpoints.

`BasicSkeletonTemplate`'s `0x0082BAE0` iterates all transforms in index order and builds one 0x30-byte transform per joint. It reads `RPRE` (`+0x28` vector), `RPST` (`+0x2C`), `BPTR` (`+0x30`), `BPRO` (`+0x34`) and `PRNT` (`+0x24`) from the loaded template. The helper at `0x00ABA9F0` performs scalar-first quaternion multiplication: the first component is `w`, with the remaining three vector components. Direct call order is `RPST` with `BPRO`, then the resulting quaternion with `RPRE`. `0x00ABA530` converts the final quaternion to a 3×3 rotation; `BPTR` supplies the translation. `0x00AB93B0` computes the rigid-transform inverse (transpose rotation and negative rotated translation).

For `PRNT = -1`, the final composition uses the external/root transform passed to `0x0082BAE0`; otherwise it uses the already computed parent transform at `parentIndex * 0x30`. The corpus confirms all parents precede children. The final composition call reaches `0x00AB9390`, an indirect optimized `Transform::multiply` dispatcher at `0x01945B04`; x86 arguments are destination, local inverse, then parent/external transform. A follow-up backend trace in `ANALYSIS_CHECKPOINT_2026-09-23_SKTM_BIND_MULTIPLY_BACKEND.md` proves the scalar order `destination = localInverse * parentOrExternal`. Renderer coordinate conversion and visual validation remain separate tasks.

The result is a much stronger behavioral model than “bind pose arrays”: the reader's quaternions and translation feed an inverse per-joint transform and a parent chain. The exact rotation-array multiplication sequence and inverse construction are **confirmed by code**. Calling the output an inverse bind transform is **strongly inferred** from the data route and inverse operation; the historical API name and final matrix convention are not proven. `JROR` is not consumed in this routine and remains zero throughout the effective corpus.

Replacement implication: retain `RPRE`, `RPST`, `BPRO`, `BPTR` and parent indices separately in the importer; compute and validate known-pose matrices only after fixing the final transform-product convention. Do not memory-map 32-bit `0x30` runtime records as a 64-bit structure. Evidence is in ignored read-only decompilations for `0x0082BAE0`, `0x00ABA9F0`, `0x00ABA530`, `0x00AB93B0`, and the `0x00AB9390` call disassembly.
