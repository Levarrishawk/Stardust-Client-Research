# Light scalar consumer: negative audit, not a closure

Date: 2026-09-24. Question A07. Static target: original `C:\Stardust-DEV\Stardust.exe` plus the configured `s207_r.dll` renderer. This is **verification/triage**, not newly closed behavioral coverage.

The prior `CLGT`/CDF checkpoints proved three authored F32 values are written to `Light +0x100,+0x104,+0x108`, but did not identify their final renderer semantics. I tested two plausible shortcuts and rejected them:

1. Windows SDK `IDirect3DDevice9::SetLight` is vtable slot `0xCC` (method index 51), but `Stardust.exe` itself uses an unrelated **graphics-raster API table** obtained by `GetApi`. Main wrapper `0x00755D30` calls that API table's `+0xCC` slot. The configured `s207_r.dll` installer `0x62A01BE0` writes `0x62A04C70` there; that function accepts two float pointers, invokes `0x62A04740` and `0x62A09E60`, and does not itself prove a `D3DLIGHT9` operation. Equating these two `+0xCC` values would be a type error. Other raw `FF /2 +0xCC` hits are terrain/UI paths, not evidence of Direct3D light submission.
2. A whole-executable Capstone candidate scan of offsets `+0x100,+0x104,+0x108` finds the known Light constructor and CLGT/CDF writers, but also camera projection, connection, crafting and other unrelated records. The only three-offset Light-class match in the `0x0076D...` method neighborhood is constructor `0x0076D500` writing defaults `(1,0,0)`; neighboring class methods `0x0076D810`, `0x0076D860`, `0x0076D880`, `0x0076D8A0` do not read the trio directly. This is a **bounded direct-access negative**, not proof the values are dead: aliased pointers, bulk copies, callbacks and separate backend uploads remain possible.

Evidence: `graphics_install_VA_007548A0` loads `s207_r.dll`, resolves `GetApi`, and stores the returned table at `DAT_01922E6C`; the raster installer writes slot `+0xCC` at `0x62B83684`. Read-only Ghidra decompilation of listed functions and scripts `tools/python/find_indirect_call_slot.py` and `tools/python/cluster_x86_field_offsets.py` reproduce the candidate search. The latter uses section-wide linear disassembly and is expressly **not** type proof. Original SDK `d3d9.h` supplies the genuine device method order.

A07 remains **open**. Next useful method: begin at the renderer's *typed collection/upload* of visible Light objects, not at coincident numeric offsets, and follow an actual Light pointer into the raster/shader parameter path. Keep the field trio neutral until that chain reaches a definite consumer. No function names, corpus counts, packet rows or percentage estimates change.

Resolution (2026-09-25): that exact typed trace was completed. Raster API slot `+0xE8` copies the selected Light pointer vector, and s207 point-light constant packing reads `+0x100..+0x108` directly as the ordered attenuation coefficient vector. See `ANALYSIS_CHECKPOINT_2026-09-25_LIGHT_ATTENUATION_CONSUMER.md`.
