# STAT PLAN records: client/server schema reconciliation (overnight block 21)

The executable's `STAT/0000` loader at `0x00B61360` processes every `PLAN/0000` record as a NUL-terminated appearance path, a three-F32 position, **four** subsequent F32 values multiplied by `pi/180`, and a final raw F32. It retains repeated records in a vector. Corpus extraction confirms all **63** effective PLAN records have the same shape: after the path terminator, eight complete F32 values and one terminal `00` byte remain. The first three floats are position; the next four are converted from degrees by code; the eighth is left raw. The terminal byte's role is unknown. It may be format padding or an unused field; preserve it in a lossless parser instead of naming it.

The current Stardust server's `MMOCoreORB/src/terrain/SpaceTerrainAppearance.cpp::parsePLAN` reads the path, three position floats, **three** degree-angle floats, then one raw float, leaving the executable's fourth degree-angle float plus the terminal byte beyond the explicitly read fields. Its `SpaceTerrainAppearance` class currently discards these parsed values and returns a constant size, so this difference is not evidence of a current gameplay failure. It is nevertheless an important schema warning: using the server parser as the sole authority for a new client would lose a client-visible transform control. The server parser's `parseCELE`, by contrast, agrees structurally on two strings, two F32s, and a three-F32 vector.

Example from `terrain/space_coruscant.trn`: `appearance/planet_gas_endor.pln` is followed by eight F32s `(2450, 1450, -750, 0, 10, 0, 0, ~1.28)` and trailing `00`. Across the effective corpus, 63 PLAN records refer to **17 unique appearance paths**, all present among the configured archive names. The `.pln` loader from block 19 handles these as separate `PLNT/0000` sphere/halo resources. This gives a concrete `STAT -> PLNT -> shader` asset chain. It does not prove every referenced planet is visible in every scene.

Confidence: **confirmed** for client read count/conversions, server source read count, corpus widths/terminal byte, path-presence check and asset chain; **unknown** for the fourth angle's specific axis, terminal byte's purpose, and runtime visibility. Do not silently normalize this mismatch or infer the trailing byte is definitely padding.
