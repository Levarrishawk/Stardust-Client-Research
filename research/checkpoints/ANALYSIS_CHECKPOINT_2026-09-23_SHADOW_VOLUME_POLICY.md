# Shadow-volume installation and policy gates (overnight block 30)

The original client has a concrete shadow-volume path, not a purely historical stub. `0x0078D3D0` installs it, registers a `ClientObject.permanentlyDisableShadowVolumes` debug flag, loads one-sided increment/decrement shaders or a two-sided shader according to a capability query, loads a screen-alpha shader, allocates render buffers, and registers teardown. Ground-environment lighting-ramp row 7 reaches the global RGBA setter `0x0078D940` (previous checkpoint); that setter also derives a nonzero-alpha gate.

The `permanentlyDisableShadowVolumes` initial value is `client_memory_budget_mb < 375`. `0x00AC18A0` returns the budget set at `0x00AC1860`. Startup either parses environment variable `SWGCLIENT_MEMORY_SIZE_MB` (`0x00401840`) or computes three quarters of `GlobalMemoryStatus.dwTotalPhys`, clamped to 250–750 MB (`0x004018B0`). The diagnostic `ShadowVolume: permanently disabled` is therefore a legacy memory-budget policy, **not** proof that this Stardust executable always disables shadow volumes. On a sufficiently provisioned default machine its initial permanent-disable bit is false. A debug flag may change it later.

There are additional gates. `0x0078D880` reports enabled only when the main shadow flag is true and either an override is present or permanent disable is false. `0x007862E0` writes the main flag based on graphics settings/capability conditions. The render path `0x0078D990` returns immediately when the main enable flag is false, row-7 alpha is zero, or its screen-alpha shader is missing. The volume-submission path `0x0078E9E0` additionally requires nonempty volume geometry and an applicable environmental/override condition. Exact relationships among all graphics-quality setting values and shadow geometry submission variants remain to be labeled.

Replacement implication: original environment assets contain meaningful shadow color/opacity, while the old 375 MB disable heuristic is not a desired 64-bit renderer constraint. A modern renderer can implement equivalent scene-level shadow intent with a different technique, but must not conflate `shadow disabled by legacy memory budget` with `authored scene has no shadows`.

Confidence: **confirmed** for install/shader branches, memory-budget source and threshold, key enable/alpha tests, and debug-flag string; **unknown** for all quality enum labels and exact one-/two-sided submission ordering.
