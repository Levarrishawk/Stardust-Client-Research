# Analysis checkpoint — Hopper/Quantity UI transaction split

Question A09 / W10+W13. This follows the [main panel](ANALYSIS_CHECKPOINT_2026-09-24_RESOURCE_EXTRACTION_MAIN_PANEL.md) and existing [resource-manager `0xED` work](ANALYSIS_CHECKPOINT_2026-09-22_RESOURCE_MANAGER_HARVESTER.md). It adds the child-panel input path and finds a **distinct Dump All command**. Target: verified original `Stardust.exe`; current server source is read-only correlation.

`SwgCuiResourceExtraction_Hopper` RTTI maps to vtables `0x015F1F68`/`0x015F1EE4`. Constructor `0x00D7FC20` binds `hopperTable`, OK, Dump, Retrieve and Dump All; activation `0x00D80110` refreshes its synchronized-UI hopper data and subscribes to `CuiResourceManager::EmptyCompleted`, while deactivation `0x00D801E0` removes that subscription and clears UI state. Button callback `0x00D802E0` validates a selected 16-byte hopper row. Dump and Retrieve open `WS_ResourceExtraction_Quantity` through `0x00D819D0` with the chosen two-dword resource ID, row quantity, and mode byte **1** (discard) or **0** (retrieve). Retrieve computes an offered maximum from row quantity capped at **100,000** in this client path; Dump passes the row's current float quantity. These are UI limits, not alterations to the server's authoritative U32 request layout. Invalid selection displays feedback rather than dispatching a request. OK closes Hopper.

`SwgCuiResourceExtraction_Quantity` RTTI maps to vtables `0x015F2040`/`0x015F1FBC`. Constructor `0x00D813D0` binds OK/Cancel, slider, numeric text box, resource name and retrieve/discard labels. `0x00D819D0` stores the selected resource ID, mode and maximum, and configures these controls. The Quantity OK callback `0x00D81980` reads the entered amount via the text control and calls `cui_resource_manager_begin_empty_VA_0099DB90(resourceId, quantity, mode, 0)`; Cancel hides without sending. Instruction-level stack inspection at `0x00D8198E..0x00D819A8` confirms that all four arguments are passed, including the mode, even though the decompiler's call display omits two. The manager's already-mapped `0xED` request, U8 token, confirmation/progress modal and `EmptyCompleted` event then apply. Both child panels subscribe to completion events during activation and unsubscribe during deactivation; the exact final widget/action response to every success/failure code remains open.

**Dump All is different.** Hopper's Dump All button opens a confirmation dialog whose callback `0x00D7FC00` invokes `0x0099DE50` for accepted response codes observed as 1 or 4. `0x0099DE50` enqueues the named `harvesterDiscardHopper` command through `0x0046E620` with the selected installation as target. It does **not** iterate rows into `0xED` requests. Current Stardust registers `HarvesterDiscardHopperCommand`; it checks installation/harvester type, admin list and 20-metre range, then clears the hopper under lock. Its policy and response shape are distinct from `EmptyHopperCallback`.

The replacement must not model Dump All as an uncorrelated series of `0xED` item discards. Preserve the two user intents and server contracts even if the UI is redesigned. No whole-client percentage change.
