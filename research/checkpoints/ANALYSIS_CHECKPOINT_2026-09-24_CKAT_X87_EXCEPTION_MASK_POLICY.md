Question A01 / W08+W02. Target: verified original `C:\Stardust-DEV\Stardust.exe`; installed CFGs searched read-only. This continues the [F32 radicand checkpoint](ANALYSIS_CHECKPOINT_2026-09-24_CKAT_F32_RADICAND_SIGN.md); it does not repeat the 248-record corpus calculation.

The executable's foundation configuration loader `0x00AA7740` reads six `SharedFoundation` booleans: `fpuExceptionPrecision`, `fpuExceptionUnderflow`, `fpuExceptionOverflow`, `fpuExceptionZeroDivide`, `fpuExceptionDenormal`, and `fpuExceptionInvalid`. Each has **default false**. None is present in the installed `C:\Stardust-DEV` CFG/INI files searched by name.

The OS installer `0x00A9FE20` calls `0x00AA7B00` after establishing main-thread identity. `0x00AA7B00` captures the prior x87 control word through `0x00AA7C00`, forms `(old & 0xF0FF) | 0x003F` (all six exception mask bits set), then clears an individual mask bit only when its corresponding config boolean is true. `fpuExceptionInvalid` controls bit 0; with the installed/default false value it remains **masked**. The computed control word is installed by `0x00AA7C20` (`fldcw`). The frame/message pump `0x00AA0720`, directly called by `frame_tick_VA_004237C0`, invokes `0x00AA7BD0` to restore that chosen word when changed.

This narrows the rare CKAT `fsqrt(negative)` issue: on the configured **main thread** after OS setup and during the normal frame pump, the invalid-operation exception is masked unless another subsystem changes the control word between restore and decode. A masked invalid operation is not by itself evidence of a synchronous floating-point trap/crash. The decoder still has no local clamp and must not be documented as producing a valid unit quaternion. Exact NaN/indefinite bit pattern, propagation into interpolation/pose matrices, and asset-loader worker-thread control-word state were **not** observed. The client asset may be decoded on a worker before main-thread publication; do not project this main-thread policy onto every thread without a call/ownership trace.
