## Code path

`0x00402FA0` is the cached playback-template fetch. It checks a CRC-string-keyed cache, tests search-tree existence, opens the asset via the common IFF path, constructs the template with `0x00404490`, and retains it. Missing files warn and return null. `0x00404490` requires `FORM PBSC` and dispatches `FORM 0001` to `0x00404750` or `FORM 0002` to `0x00404DF0`. The observed v0002 grammar includes `INFO`, `FORM VAR ` with optional `STRN`, `FLOT`, `INT ` chunks, and `FORM THDS` containing `FORM THRD` action sequences. The v0002 `INFO` reader obtains a 16-bit count and then one byte per entry; v0001 initializes the corresponding entries to one. The physical meaning of those bytes is not yet established. Version and chunk boundaries are **confirmed by code**; the decompiler's local-variable names are not original types.

Within each `THRD`, `0x00404DF0` reads the next action-form tag, looks it up in the action-factory registry via `0x00407090`, invokes the registered factory, and retains the resulting action template in the thread sequence. The lookup misses at the registry sentinel and the parser takes an `unknown action template type` fatal diagnostic branch. `0x00404130` inserts an action tag/factory pair into that registry. Direct executable cross-references to this insertion function identify 25 registrations, including `FIPR` (`FireProjectileActionTemplate`) and `SOAT`; both are absent from the effective `.pst` corpus. This is an inventory of direct registrations in this executable, not a proof about dynamically loaded code.

There is at least one concrete runtime consumer: `0x00467370` fetches a script template from a retained path at its object's `+0x04`, returns without creating a script if fetch fails, otherwise constructs a playback instance via `0x00404200` and applies retained actor/variable data. `0x00469E80` also fetches script templates while building a retained vector; that path looks like prefetch and is not evidence of playback by itself. The full trigger-to-completion runtime, including every action's side effects and timeout policy, remains outside this block.

The common playback scheduler is nevertheless visible. Ground-scene update `0x0051AF10` calls `0x00401AB0`; this iterates the manager's active-script vector, calls instance update `0x004078C0`, and retires entries whose update reports no continuing thread. In `0x004078C0`, each thread has a current action index and elapsed time. The current action's virtual `+0x10` method is called with frame delta and script context; a continuing result accumulates elapsed time and is compared with virtual `+0x18` (a duration/timeout-like value). A completed or over-limit action advances the thread index, potentially processing another action in the same update. The return indicates whether any thread remains active. This **confirms scheduling shape**, but the exact contract of every action's virtual methods and exception behavior requires separate action-family work.

## Installed corpus

`tools/python/pst_overlay_inventory.py` replays the 48 existing `searchTree_00_*` archive mounts from `swgemu_live.cfg` in descending priority, honoring first-name wins. It finds **32 effective `.pst` entries**, all structurally valid `PBSC/0002`, with **68 `THRD` sequences** and **124 action forms** spanning **25 distinct action tags**. No `PBSC/0001` script is effective, although this executable has a reader for it. The most common action is `PSKA` (42). The complete counts are reproducible with the tool; they should not be treated as action-success counts.

One installed file, `playback/fire_projectiles_location.pst` from `mtg_patch_017.tre` (configured priority 46), contains `FIPL` and `PPRL` action forms once each. Neither tag appears in the 25 direct registration values, and raw-tag checks found neither spelling/reversed immediate in `Stardust.exe`. The known registry lookup/fatal path means that **if this exact file is loaded by this executable under the observed registry**, these tags would be unrecognized. This is a **strong inference**, not a witnessed crash: an indirect/dynamic registration path or runtime reachability has not been ruled out. A literal-reference scan of installed TRE payloads and the current Stardust server source found no reference to the path, and the executable itself contains no literal path, so it may be dormant. Do not silently discard the file in a replacement asset pipeline; preserve it and resolve its action semantics or explicitly classify it as unsupported after reachability testing.

## Confidence and next boundary

- **Confirmed by code:** PBSC versions 0001/0002, v0002 thread/action factory dispatch, cache fetch and null return on missing script, 25 direct registrations, unknown-tag diagnostic branch, one runtime instantiation path.
- **Confirmed by configured corpus:** 32 effective v0002 files, 68 threads, 124 actions, the one `FIPL`/`PPRL` file and its overlay source.
- **Strongly inferred:** loading that file with only the observed direct registry would enter the unknown-tag branch.
- **Unknown:** whether the file is reachable in ordinary Stardust play; any indirect action registration; exact v0002 `INFO` byte semantics; complete runtime and all 25 action contracts.

Replacement implication: represent `PBSC` as typed script/thread/action data and separate asset decoding from action execution. Unknown action tags must be retained and surfaced in diagnostics, not misparsed as a different action. A modern client need not duplicate the original x86 object layout or manager container.
