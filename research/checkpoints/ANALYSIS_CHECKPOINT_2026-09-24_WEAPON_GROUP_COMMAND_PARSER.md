# `/weaponGroup` parser: local group editing versus firing controls

Date: 2026-09-24. Scope W10/W13. Verified original `C:\Stardust-DEV\Stardust.exe`; Ghidra output is reconstructed pseudocode. This extends the prior [ship weapon-group manager/UI checkpoint](ANALYSIS_CHECKPOINT_2026-09-22_SHIP_WEAPON_GROUPS.md), which already established local `SWGI` persistence.

`SwgCuiCommandParserShipWeaponGroup` constructor `0x010E2510` registers root `WeaponGroup`; parse function `0x010E25C0` has 13 exact subcommand strings recovered from its executable pointer table (`0x015F96C0..0x015F96F0`): `info`, `defaults`, `add`, `remove`, `clear`, `fire`, `fireProjectile`, `previousProjectile`, `nextProjectile`, `fireMissile`, `fireCountermeasures`, `previousMissile`, `nextMissile`. This is a local console/input grammar, not 13 protocol opcodes.

The parse function requires a current player/ship context. `info` enumerates selected/current group information into the command-output buffer. `defaults` chooses manager reset or ship-specific default group setup based on its argument. `add`, `remove`, and `clear` parse numeric group/weapon-slot values, reject invalid ship or group IDs and reject weapon slot outside 0..99, then call the existing `ShipWeaponGroupManager` selection/mutation methods in the `0x006F34xx..0x006F41xx` range. These are local `SWGI` configuration operations, as previously established from manager persistence; they are not server group-assignment requests.

The remaining verbs act on firing/selection state, not the membership file. `fire` and `fireProjectile` pass through `0x0058A8C0` / `0x0058AC90`, `fireCountermeasures` through `0x0058ACB0`, and projectile/missile previous/next through `0x0058AE50` with a type/direction pair; `fireMissile` also enters that selection family after a readiness call. The downstream ship fire helper `0x0053B950` **can** enqueue the literal ordinary command `openWings` under a network-mode readiness branch (`0x0046E5F0`); this is not itself proof of a weapon-fire command packet. The same helper performs local simulation/weapon-effect work. Thus “the parser itself has no packet constructor” must **not** be mistaken for “firing never reaches the server.” The actual ship-fire message variants still require their own bounded trace.

Replacement separation: keep the original command grammar as an optional compatibility input surface; store group membership/profile locally using `SWGI` semantics; route firing verbs through the modern ship-control layer, preserving the established server-visible firing contract rather than turning group edit verbs into wire requests.

Cross-reference: the later ordinary-fire branch of `0x0053B950` reaches `0x00597A60`, the previously documented client/local projectile route that can emit `CreateProjectileMessage` (`0xB88AF9A5`) when appropriate. This identifies an existing downstream protocol bridge for projectile fire without claiming that every parser verb or every fire attempt emits that packet. See [ProjectileManager](ANALYSIS_CHECKPOINT_2026-09-21_PROJECTILE_MANAGER.md).
