## Rules for new blocks

1. Before starting, select an **open question ID** below and read its cited prior evidence. Record the exact observation that is missing. A previously closed boundary is not a new block merely because it is checked again.
2. A block may **close** a question only with new executable instructions, original-asset bytes/corpus evidence, server-source correlation, or a bounded runtime/differential fixture sufficient to decide its stated criterion. Give addresses/paths, confidence and negative evidence where relevant.
3. Revalidation, corrections and contradiction audits are valuable, but label them **verification/correction**, not new breadth. If an old conclusion changes, amend the durable document and cite both the superseded and replacement evidence.
4. Distinguish **sub-boundary closed** from **workstream closed**. One asset grammar, UI mediator or packet handler does not close its entire parent subsystem. Record remaining paths in the same checkpoint.
5. Do not increase a whole-client percentage from block count, function-name count, or asset-file count alone. Rescore the affected weighted workstream against its exit criterion and show the arithmetic and residual denominator. Do not infer that every raw compiler function must be named.
6. Keep the original executable and assets read-only; do not start a replacement build or engine choice from this inventory. The user handles Git commits.

Status vocabulary: **closed boundary** = specified observable contract is evidence-backed; **partial** = important contracts known but named gaps remain; **open** = material behavior is not yet established; **conditional** = installed data exists but ordinary reachability is unproven. Confidence describes the *known result*, not the gap. “No new block” means consult the cited work first; it is not a ban on correcting it.
