# World presentation drain ownership

Round20 Runtime, October2,2026. [Consumer](../../SWG-Godot-Client/poc/Stardust.Core/Session/SceneWorldObjectPresentationConsumer.cs) now observes the optional frozen [drain interface](../../SWG-Godot-Client/poc/Stardust.Core/Session/ISceneWorldObjectPresentationDrain.cs) after every adapter disposal attempt. [Pump](../../SWG-Godot-Client/poc/Stardust.Core/Session/SceneWorldPresentationPump.cs) combines presentation drain and coordinator drain after close. This is modern ownership policy; no original scheduling, schema or rendering behavior is inferred.

The consumer constructor appends `int? maximumDrainingPresentations = null`. Null means twice maximumActors:128 by default, at most8,192. An explicit limit must be at least maximumActors and no greater than8,192. Before a new factory invocation, admission requires `pending retired tasks + currently owned actors + one possible candidate <= drain limit`, in addition to the existing actor limit. Every actor reserves eventual cleanup space; replacement also reserves rollback of the candidate while the old actor is still owned. Already accepted exact publications remain idempotent. Capacity rejects with InvalidDataException before invoking the factory. A direct caller may complete pending work and retry; the pump's existing failure policy closes on this error. Synchronous adapters retain existing behavior and consume no pending task after retirement.

Every path uses one disposal helper: candidate false/wrong/stale/throw rollback; replacement; stale Tick/batch/Count/Find boundaries; reset; RetireAll; Dispose. Ownership detaches before cleanup, then Dispose is attempted and the optional DrainCompletion getter is called exactly once, even when Dispose throws. Clear still attempts all detached actors. Drain capture occurs on the serialized owner thread inside the callback reentry guard. Dispose/getter errors propagate, together when both fail. Null/throwing task getters leave a sticky failed completion, because unavailable worker ownership cannot be described as successfully drained. Such an adapter must honor the interface promise that its task remains observable after disposal. A factory that throws before returning an adapter retains its existing responsibility for those unreturned allocations.

`DrainingPresentationCount` and `DrainCompletion` are owner-thread getters usable after disposal. Pending tasks deduplicate by reference. Completed tasks are reaped at boundaries, admission, retirement and getters; they do not form a tombstone history. One first-failure diagnostic is retained; every later task fault is observed even when not retained diagnostically. Cancellation also rejects a successful drain. Observed asynchronous failure makes subsequent active consumer boundary operations fail with InvalidDataException; explicit RetireAll/Dispose and drain inspection remain available. The pump catches this failure and closes. Direct consumer callers must explicitly dispose their remaining owned actors after a drain failure.

Overlapping retired tasks share one completion group. Each worker task attaches one group counter continuation and a fault observer; neither callback mutates the actor dictionary or invokes adapters/world APIs. A small locked group counter settles one TaskCompletionSource, with asynchronous downstream continuations, when every task in that group finishes. Repeated reads and completed-worker churn behind one long worker return that same task rather than allocating successive WhenAll snapshots. The consumer retains only its bounded pending-task list, one current group and one sticky failure; it retains no retired adapter objects. Diagnostic exception payload size, adapter-private ownership and caller-retained task references are outside the logical bounds.

A read during operation covers the current retired group, which can include later retirements while still pending. It does not promise to drain actors not yet disposed or all future groups. After consumer Dispose, obtain DrainCompletion to await every task captured by that cleanup. A faulted/canceled completion represents failed cleanup, never successful drain. An inaccessible task getter can prevent proof of complete worker cleanup; its failure remains explicit.

Pump Close marks closure, clears owned queued message bytes/publications/callbacks, attempts both consumer.Dispose and world.Close, then captures both drains independently and exposes one stable `Task.WhenAll`. Cleanup errors still throw AggregateException synchronously; this does not remove the drain handle. That handle waits for every known presentation and world task even when one faults. Caught pump reentry newly attempted during disposal/getter callbacks is also reported after both cleanup attempts. Existing already-reported Step reentry is not counted again. Repeated Close/Dispose leaves the same completion. Before close, the getter exposes the consumer's current retired group; final world-drain semantics require Close. Existing synchronous disposal exceptions retain their prior synchronous error channel; they do not independently turn a successful worker drain into a task fault.
