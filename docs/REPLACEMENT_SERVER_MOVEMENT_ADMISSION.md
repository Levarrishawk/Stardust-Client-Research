## State and validation prerequisites

Observation: `DataTransform.h:158–242`, `run`, requires player, zone, ghost, nonnull last validated position, and `teleporting=false`; it filters the parent to mount/vehicle and locks it when present. Forced-transform mode takes the last validated position instead of the ordinary player-position snapshot and is cleared afterward. Interpretation: use an ordinary unmounted, uncontained selected human with matched current/validated outdoor positions and no forced transform. Confidence: Confirmed branch observations; Strongly inferred scenario choice. Consequence: do not silently use parent or forced-transform paths as substitutes for missing lifecycle readiness.

Observation: `DataTransform.h:246–311`, `updatePosition`, validates coordinates; when not forced, it requires posture accepted by `Transform.h:144–156` (0 upright,1 crouched,2 prone,3 sneaking,8 sitting,9 skill-animating) and applies inertia when delta<400. Nonprivileged characters must not be frozen, need an inventory, and must have recursive count≤volume limit+1. All characters require `isMovementAllowed`, planet manager and player manager. `MMOCoreORB/src/server/zone/objects/creature/CreatureObject.idl:1512–1514` defines movement allowed as the next-allowed-move time being past. Consequence: choose upright0, unfrozen, normal inventory, no animation/movement lock; do not claim all admitted postures are equivalent playable states.

Observation: `DataTransform.h:324–335` calls speed validation and rejects INVALID_POSITION, then rejects a nonpassable terrain path when a terrain manager exists. `MMOCoreORB/src/server/zone/managers/player/PlayerManagerImplementation.cpp:4215–4305`, `checkSpeedHackTests`, uses **server elapsed time** from the last validated movement timestamp. Consequence: client timestamp and server elapsed clock are separate; do not simulate server admission with timestamp-only arithmetic.
