Current/validated position, effective posture/speed/inventory and floor/path prerequisites remain required.

## Outer word versus counter: preserved discrepancy

The recovered common client envelope has a separate four-byte outer scalar at wire0x16; this sender supplies scalar zero to the queue and a typed payload that serializes another four-byte counter. Current server `MMOCoreORB/src/server/zone/packets/object/ObjectControllerMessageCallback.cpp:18–23,48` parses priority/type/ID and delegates without consuming a separate scalar. `packets/object/TeleportAckCallback.h:19–36` consumes just the first U32 after ID into its unused movementCounter member, then clears teleporting. Thus the server can clear the flag without using the typed received-counter value; its field name and the historical “occupies scalar position” row do not prove that the client omits the common scalar or overlays its payload there.

**Confirmed:** typed four-byte counter serialization, queue scalar0 and priority23, and server's first-word consumption/unused value. **Strongly inferred:** common client outer scalar plus typed counter can leave an extra four bytes beyond what this server callback reads. **Unknown:** exact final0x13F wire extent and any packer special case, because this bounded probe did not follow the queue-to-network packer. No complete ACK byte fixture is promoted. Exact next probe for later-teleport implementation: follow the actual outbound record's common packer/constructor to determine whether outer scalar and typed counter are both emitted and retain deterministic exact bytes. No original execution/capture is needed to resolve that static question.
