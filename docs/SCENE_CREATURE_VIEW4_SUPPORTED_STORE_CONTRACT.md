# Scene CREO4 supported prepared store

SceneCreatureView4SupportedReplicationStore (external historical reference) owns immutable supported CREO4 models and ordered journals over a borrowed serialized SceneObjectRegistry (external historical reference). It delegates to the accepted [supported state](CREATURE_VIEW4_SUPPORTED_CONTRACT.md). Supported delta fields are the eleven scalar fields, field2 encumbrances and field3 skill map. All fourteen baseline fields remain represented, but mission field13 is retained unchanged and cannot be applied through this store. No world route, delivery callback, field13 kernel, engine adapter or live connection is added.

## API and identity

Constructor accepts registry, optional SceneCreatureView4SupportedStoreLimits, optional CreatureView4SupportedStateLimits and global revisionSeed. Limits and nested model/message records are validated and copied. Defaults:64 actors,1MiB logical state,4096 pending/per-apply events,2MiB logical output,1048576 work. Store hard ceilings:4096 actors,128MiB state,262144 pending/per-apply events,256MiB output,16777216 work. State/output minimum8; the actual empty supported model requires72. Work/events may be zero. Child model/message ceilings remain their frozen narrower ceilings.

Public operations: Seed(handle,baseline), Apply(handle,exactExpectedSnapshot,plan), Find(handle), IsCurrent(snapshot), Revision, RetainedStateBytes, PendingEventCount, PendingEventBytes, DrainEvents(), Acknowledge(batch), IsCurrentEvent(batch,index), Close()/Dispose(). All require the constructing managed thread and reject reentry. The host must serialize borrowed registry mutations with store operations. There are no callbacks inside this store.

Snapshot exposes Handle, Incarnation, global Revision and immutable State. Seed requires the exact current registry handle and matching baseline ID. Apply additionally requires this store's exact stored snapshot reference and matching current incarnation. Stale handles, foreign/superseded snapshots or recreated incarnations return null before accessing baseline/plan; current identity with null or wrong-recipient input throws. A valid seed or whole apply advances checked global and full-state revisions once, including skipped/no-op/counter-only messages. Same-incarnation reseed continues prior state revision; recreated objects start state revision1 without rewinding global revision.

Same-incarnation handle updates preserve state. Find(newCurrentHandle) returns its historical-handle snapshot, whose IsCurrent is false until a new publication. Apply(newCurrentHandle,thatExactStoredSnapshot,plan) remains allowed. Historical events use incarnation currentness, so same-incarnation handle changes do not invalidate their recipients. This matches the accepted [CREO6 lifecycle reference](SCENE_CREATURE_VIEW6_FULL_STORE_CONTRACT.md); fixed CREO6 event sizing is not reused.

Find, IsCurrent, RetainedStateBytes and DrainEvents retire stale incarnations. Revision, pending count/bytes and writes do not prune. Retirement prebuilds replacement map/totals and checked epoch before assignment, invalidates issued batches, leaves global revision and historical journal unchanged. Failed writes leave stale actors retained until a read retirement; actor capacity can therefore remain occupied. Close releases store references while preserving last global revision and leaving borrowed registry open. Previously returned immutable values may remain caller-owned.

## Genuine prepared publication

Internal Prepared, PrepareSeed, PrepareApply, CheckPrepared, CommitPrepared and ReleasePrepared implement the seam. Preparation holds the owner gate until release and builds the complete supported result, replacement snapshot/map/journal, all logical capacity totals and checked next global revision/epoch before any publication. Candidate identity binds this store, exact handle/incarnation, active slot and proposed revisions.

CheckPrepared requires owner thread, held gate, open store, exact owner/active candidate reference, unconsumed candidate, checked next revision/epoch and current registry handle/incarnation. CommitPrepared rechecks these conditions immediately, then only assigns prebuilt map/state charge/journal/revision/epoch and clears issued identity before marking consumed. It invokes no callback or user code. Public Seed/Apply check, commit and always release in finally. A failed check or release without commit publishes no prefix. Foreign/cloned/released/reused/consumed candidates reject; foreign or wrong-thread release cannot unlock an active candidate. Reentrant reads, close and preparation reject while held. The borrowed registry remains externally mutable only under the host's serialization rule; mutation between prepare and commit is caught by revalidation.

Preparation failure, late child error, policy rejection, global/state revision or epoch overflow preserve published snapshots, totals, journal and issued receipt. External registry mutation itself is not rolled back. Reflection fault injection exists only in the own runner, never as production test accessors or a frozen assembly edit.

## Variable journal and global accounting

RetainedStateBytes is the sum of all owned states' DecodedBytes. Supported state cost is72+4*encumbranceCount+16*missionCount+16*skillCount+keyBytes. Raw seed duplicate records and key bytes consume the frozen seed validation capacity/work before skill-map normalization. Supported runtime skills use canonical byte-ordered unique keys with last duplicate value; raw baseline codec bytes/prefix spelling are not changed.

Each Assignment/EncumbranceMutation event costs48 logical bytes; each SkillMutation costs64+Name.Length. PendingEventBytes sums those actual costs, including historical events from retired actors. Effective child state capacity subtracts every other retained actor; effective output subtracts those actor bytes plus all prior pending event bytes. Pending/per-apply event limits narrow the child event ceiling. Before allocating replacement map/journal, the store rechecks actor count, final state, pending/per-apply event counts and state plus actual queued event bytes. A candidate cannot hide key-dependent costs or stale other actors.

The frozen supported kernel enforces initial, intermediate and final full-state peaks, full64+key mapped descriptions, narrower32+key map construction summaries and24-byte encumbrance summaries. The store narrows its limits without replacing these reservations with final-state-only sizing or a fixed event multiplier. Insert then remove and late invalid command tests reject atomically when an intermediate peak exceeds capacity.

MaximumWork narrows both frozen full-state work and independent message work ceilings. Full apply already charges message consumption; it is not charged twice. Seed retains complete raw/normalized validation plus exact child seed lookup/copy costs. Map/journal wrapper scans/copies are separately hard-bounded by actor/event maxima, as in the accepted lifecycle reference. Work and bytes are logical policy units, not total CLR heap, CPU time or lifetime accounting. No new work receipt is exposed by the store; tests independently replay child WorkUsed and verify seed work with exact/one-less limits.

## Journal ownership

Each event record retains publication Handle, Incarnation, StoreRevision and the complete immutable supported event value, including binary Name, old/new scalar/vector bits or signed skill pair values. It retains no model, plan, callback or resolver reference. Event batch exposes global StoreRevision and readonly Events; internal owner/epoch bind exact issuance.

Drain returns the same issued batch until publication, retirement or acknowledgement invalidates it. Acknowledge requires exact store/issued reference and current revision/epoch, clears the whole journal exactly once, and rejects foreign/stale/repeated/closed receipts. Empty batches also acknowledge once. Registry destruction alone does not revoke historical journal ownership; before retirement an issued receipt can still acknowledge. IsCurrentEvent additionally requires in-range index and current registry incarnation, excluding obsolete delivery. No finalized phase or world generation is implied; a future host must add its own delivery guard.
