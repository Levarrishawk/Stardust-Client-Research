# Opt-in received-only CREO4 world admission

SceneWorldCoordinator (external historical reference) can own the accepted [received-only partial store](SCENE_CREATURE_VIEW4_PARTIAL_STORE_CONTRACT.md). This prototype closes observer scalar admission without inventing a full baseline, defaults, collection semantics, or gameplay effects. The default remains opaque. Full4 and partial4 policies are mutually exclusive; full6 and existing typed3 modes can remain independently enabled.

## Policy and receipts

Pass `SceneWorldCreatureView4PartialPolicy(StateLimits, StoreLimits, RevisionSeed=0, MaximumWorldBytes=134217728, MaximumWorldWork=16777216)` as the optional final `creatureView4PartialPolicy` constructor argument. Both world constructors support it. The copied message limit must fit the world's maximumPayloadBytes; configure it explicitly (for example MaximumPayloadBytes65536 for the default world ingress bound). The store validates copied partial/store hard limits. World byte/work bounds are modern logical accounting, not managed memory measurements.

`CreatureView4PartialEnabled`, `FindCreatureView4Partial(generation,id)`, `IsCurrent(snapshot)`, `ApplyCreatureView4PartialDelta(generation,expected?,plan)`, `RetainedCreatureView4PartialBytes`, `RetainedCreatureView4PartialWorldBytes`, and `LastCreatureView4PartialWork` expose the opt-in path. Object snapshots also expose CreatureView4Partial. A receipt carries world generation, store publication revision, immutable partial State and store WorkUsed. LastCreatureView4PartialWork records the most recent successful partial admission's combined work and resets with scene clearing/close.

Direct Apply requires an active AwaitingServerReady/Ready world, a current creature recipe recipient, and exact expected receipt. Null means first state in the exact incarnation, never overwrite. Stale generation or foreign/stale/null-overwrite receipts return false. Eligible invalid plans throw. Raw world Accept resolves the current exact receipt internally. Both PendingBaselines and Finalized phases are admitted. No full4 seed or barrier is required; unknown fields remain unknown and received zero remains known.

World wrappers identify the exact underlying store publication, generation and incarnation. Registry handle-only changes preserve state currency. Replacement/destroy-recreate resets observations for that incarnation. World lifecycle retires stale retained store state and its matching publication map; a failed partial write does not prune unrelated stale partial entries to meet budgets.

## Preparation and global reservations

Frozen whole-plan measurement validates scalar indices and widths. Checked world mutation revision and world change-slot capacity are reserved before store preparation. Let N be assignments, K final known target fields, A retained partial publications, P pending partial journal records, C pending world change slots, and I first publication in this incarnation.

- Store work remains `23+6*N+K+11*I+A+P`.
- World overhead is `1+2*N+C+A`: lookup, whole-plan measure/mask prediction, change-map copy and publication-map copy.
- Combined work is their sum and must fit MaximumWorldWork.
- Prospective world bytes include all partial actor states, all old/new partial journal records at64 bytes each, existing opaque-envelope bytes, retained typed3/TANO3/typed6 state and their supported event accounting, plus32 bytes per prospective world change slot.

MaximumWorldBytes is checked against that complete prospective aggregate for each partial admission. Other packet families retain their existing independent limits; this opt-in policy does not add a universal memory monitor to unrelated mutations. Store object/state/pending/per-apply/output/work limits and kernel/message limits also apply. The dedicated partial retained counter includes state and journal; the world retained counter includes the aggregate above.

The coordinator keeps an exact publication map so eligibility and prediction do not invoke read-side partial-store retirement before a write. It calls real PrepareApply/CheckPrepared, verifies predicted bytes/event count/work against the prepared candidate, builds world dictionaries, rechecks, and invokes CommitPrepared. Callback-free prebuilt assignments publish store, exact world publication, coalesced world change and mutation revision together. Finally ReleasePrepared handles both commit and cancellation. Allocation or validation failure before commit leaves publication and world change semantics unchanged. Host/world/store owner-thread serialization is required; these are not parallel synchronization APIs.

## Ingress, ordering and failure policy

SceneWorldCreatureView4PartialApplicationRouter (external historical reference) owns a copy of bounded ingress bytes, borrows world/downstream, and clears its copy in finally. During Initializing, exact CREO4 candidates are forwarded directly to the authorized world Accept staging path: no live registry or receipt is required and the optional decoder is not invoked. Owned bytes, world staging count/byte limits and replay failure policy are preserved; scalar grammar is validated by ordered replay. For active ingress, it parses the frozen scalar grammar before invoking an optional decoder. World generation/state/revision/callback stamp, exact registry object and partial publication currency are revalidated after callbacks. Plan object ID, raw declared count and every ordered field/raw-bit pair must equal the parsed wire plan: decoder transformations are rejected. Swallowed router reentry, world lifecycle/transform/reset, world or partial-journal acknowledgement, foreign plans and close cannot publish. Noncandidate messages go to downstream. Any ingress exception closes the router, while the borrowed world follows its own failure policy.

The complete deterministic observer sequence passes through this router, including start and every initialization message. Its ordered replay is create, containment, CREO3 baseline, CREO4 scalar fields1/5/10, CREO6 baseline, SceneEndBaselines. Staged messages do not publish before CompleteMinimumSceneBarrier. Ordered replay creates partial state while the object is PendingBaselines; end changes the handle but preserves incarnation/state. The special observer fixture retains negative-zero and NaN payload bits deliberately; it does not claim those words are emitted by a compiled server. CREO3/6 fixture messages are validated frozen complete baselines and remain separately opaque in this particular suite. A separate test enables full6 and confirms it remains current across partial4 updates.

Partial mode rejects every full4 baseline atomically with the explicit received-only exclusion error. Collections2/3/13 remain rejected by the frozen scalar codec. Active identified typed4 malformed/full-baseline failures preserve the world and previous receipts. An unidentifiable malformed/control failure can use existing fail-and-clear behavior. Any ordered initialization replay failure clears the whole scene, partial state and journal. Resource preparation failure does likewise when its completion is polled; the first poll starts work, a subsequent poll observes its fault. Cancellation/reset clears scene partial state/journal and cancels resource ownership. Outstanding cancellation-ignoring work follows the existing initializer drain contract. Close clears partial publication and journal, invalidates receipts, and disposes owned world resources.

## Journal and delivery

`DrainCreatureView4PartialEvents`, `AcknowledgeCreatureView4PartialEvents`, and `IsCurrentCreatureView4PartialEvent` wrap exact store batches with world owner/generation. Each received assignment is retained, including equal values; source revision/declared count/ordinal and old presence are unchanged. Delivery requires active world, exact issued store batch and current incarnation in PendingBaselines or Finalized. Destroyed historical records remain drainable/acknowledgeable but cannot deliver. A later write or retirement invalidates prior issued batches. Scene reset deliberately clears the historical journal and invalidates old generation wrappers. Host delivery/lifecycle must remain serialized.
