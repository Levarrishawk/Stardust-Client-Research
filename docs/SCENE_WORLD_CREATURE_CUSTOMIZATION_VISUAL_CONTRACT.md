# World creature supplied customization presentation

[SceneWorldCreatureCustomizationVisual](../poc/Stardust.Godot/SceneWorldCreatureCustomizationVisual.cs) owns an accepted `SceneWorldLocomotionVisual`, borrows the world coordinator and frozen `ISceneWorldCreatureCustomizationSource`, and implements presentation plus optional asynchronous drain. Construction requires the exact current incarnation/publication, a live published creature root, owned generated-face/material resources, and a describable color/style control union. Failed construction preserves the caller's inner ownership. All construction and presentation operations require their creating Godot main thread; reentry is rejected.

The ordinary constructor is `(world, inner, source)`. An optional CPU composer delegate supports controlled diagnostics; production uses the existing `SkeletalAppearanceCustomization.Apply`. `Inner`, `LastAppliedRevision`, `LastFailure`, and `GeneratedFaceSha256` expose the accepted state. The hash is the single committed face's CPU RGBA SHA-256; it is null for multiple face outputs. It changes only after a successful commit and remains available after disposal. It does not replace `SceneCreatureVisual.Verify(true)`, which verifies the actual GPU shader binding/readback.

## Revision and worker policy

Values are explicit immutable supplied snapshots; they are separate from raw replication/CIDM bytes and the validated face-only resource-completion policy. `DescribeControls` supplies the exact face/material namespace union. The original human union has eight keys, including distinct public/private skin keys and material-only color keys. Missing or additional keys fail without a worker submission. Values outside a control's ordinary range use existing per-consumer fallback rules; no authored defaults are introduced.

The adapter retains one latest observed immutable snapshot, one requested snapshot, and a monotonic incarnation-local high-water revision. Same-revision different values are rejected even after success or failure. Older, missing, or foreign-incarnation values retain the current appearance and invalidate pending work. Reappearance at the same invalidated revision does not resubmit it; recovery requires a newer revision. Composer and GPU-boundary failures retain the accepted appearance and `LastAppliedRevision`, report `LastFailure`, and do not retry each frame. A newer valid snapshot can recover.

The existing [revision owner](LIVE_SKELETAL_CUSTOMIZATION_CONTRACT.md) runs one composer with one replaceable pending snapshot. If missing/stale input disposes that owner, the adapter retains exactly one retiring task. It may retain a newer replaceable supplied snapshot while that task runs, but creates no new revision owner until retirement settles. Completed fault metadata is observed and released when starting the next owner. Thus repeated disappearance cannot accumulate concurrent noncooperative workers or a task history. Disposal cancels/clears pending work, drops world/source/base/composer references, and owns inner disposal. `DrainCompletion` remains observable afterward, includes the retiring CPU task, and completes only when that task settles; cancellation alone does not imply completion. The active drain property is a snapshot of currently running work and must be read on the owner thread; after disposal the frozen task can be awaited elsewhere.

Each frame first delegates motion, Height, and animation to the accepted inner. Before transferring a ready CPU result it rechecks current world/incarnation, queries the borrowed source again, and requires the same exact revision and values. Newer or missing values appearing during that final query discard the result. No await occurs between freshness checks and GPU commit.

## GPU commit and retained state

The added [SceneCreatureVisual.ApplyCustomization](../poc/Stardust.Godot/SceneCreatureVisual.cs) verifies that all immutable descriptor fields still match its original base, allowing only material selections, generated faces, and customization values to differ. It invokes the existing mesh/material transaction and stores the owned CPU appearance revision only after GPU success. The existing transaction validates retained materials/effects/original textures/programs, factor identities, generated binding destinations, and RGBA output shape; it prepares uploads before uniform changes and rolls back commit failures.

Customization preserves pose, placement/Height, animation clocks, topology/UVs, mesh/material/shader identities, and original texture identities. Generated face texture identities may change and old generated uploads are released. Comparing a fingerprint that includes all texture IDs across successful customization is therefore inappropriate. The [standalone proof](../poc/Stardust.Godot/SceneWorldCreatureCustomizationPreview.cs) hashes retained resources and uploaded topology/pose separately from the generated face texture, and verifies the full GPU boundary after accepted and rejected updates.

## Reproduction and bounded evidence

Use existing cached .NET 8, Godot 4.7.2 Mono, and bundled Python. Generate the synthetic application peer with [the baseline producer](../poc/round18-tests/Rendering/Generate-Peer.py), then use the own [launcher](../poc/round20-tests/Rendering/Launch.ps1):

```powershell
python poc/round18-tests/Rendering/Generate-Peer.py local-private/round20/peer.json
dotnet build poc/Stardust.Godot/Stardust.Godot.csproj --no-restore -p:NuGetAudit=false -v quiet
./poc/round20-tests/Rendering/Launch.ps1 -GodotPath $taskGodot -ArchiveRoot C:/Stardust-DEV -Configuration C:/Stardust-DEV/swgemu_live.cfg -FixturePath local-private/round20/peer.json
```

Set a task-private APPDATA before building. `$taskGodot` is the explicit existing replacement-engine console executable. For GPU evidence add `-CapturePath` with a fresh absolute PNG under the checkout's existing ignored private directory. The sibling capture appends `-varied`. The launcher prints the private log and export paths. Run [Verify.py](../poc/round20-tests/Rendering/Verify.py) with the export, zero PNG, and varied PNG. No original executable or server is involved.

The accepted resource route loads 76 sources / 5,940,390 bytes under explicit 128-source / 32 MiB encoded and separate 64 MiB decoded policy. Full zero and varied profiles are supplied inspection choices, not recovered player values. Independent original-byte preparation agrees for five shader slots/nine operations per profile; composition agrees for five layers and each 256×256 RGBA output. Zero digest is `A41EE8925C695A8BC2DA0CAC1FA17864D471270507DF3900472F0655A5A42808`; varied is `60C109DF85346F25B814E303B6D022D7D2D94459234790B6337ABB1877E7B8F5`.

At identical idle frame 0, Height 1, camera/FOV/background, GPU captures differ at 48,398 pixels: 3,090 in the sampled face rectangle and 44,861 in the sampled body rectangle. Silhouette and background masks are identical. Controlled tests prove rapid revisions 2/3/4 publish only 4, nine missing/new transitions retain one active composer, same-revision mutation after success/failure is rejected, missing/older/foreign values retain display, and source change during final commit query discards ready output. Composer failure, altered immutable source closure, and malformed generated RGBA reject without replacing accepted display. Walk/run, focus freeze, Height 1.4, clock reset, and explicit zero reset pass. Incarnation loss disposes the root while noncooperative CPU work remains awaitable; final drain balances one root and one archive.

This establishes supplied color/style presentation over accepted assets.
