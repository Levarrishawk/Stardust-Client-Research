# Explicit replacement-client bootstrap

The separate bootstrap scene (external historical reference)
composes the original-installation preparation, engine-neutral application and
[prototype host host](REPLACEMENT_PROTOTYPE_CLIENT_HOST_CONTRACT.md). The project main scene
is unchanged. The accepted injected offline API remains available. Opening the
scene with one explicit controlled-launch JSON path visibly refuses transport.
Round93 adds an explicit opt-in composition; its real UDP constructor branch is
written and source-reviewed only. No socket construction or contact is executed
in the Round93 proof.

## Explicit standalone admission

Direct user arguments must be exactly `--controlled-transport`, one absolute
controlled-launch JSON path and one absolute new diagnostic JSON destination.
The opt-in is an application admission switch, not live-task authorization.
The destination must be inside a `local-private` directory with an existing
parent. Missing/extra/unknown arguments, malformed inputs, existing files or
directories, UNC/URI/traversal/ADS/device/ambiguous paths and linked ancestors
reject before installation preparation or any factory acquisition. Default
one-path startup still refuses contact; no automatic Login is emitted.

`ConfigureStandaloneOffline(arguments, spyFactory, explicitTestClock,
explicitOfflineMinimumGate, explicitTestRootPolicy)` is the narrow native replay
seam. It takes the same three arguments through the same admission and application
composition as direct startup. The factory is mandatory and the status/receipt
are unconditionally synthetic/offline. The shared factory validates the fixed
approved numeric peer for each connection, then returns the spy result; this
branch cannot fall through to `new UdpDatagramPort()`. In future direct admitted
startup the constructor is lazy at application acquisition and never resolves
hostnames. Its actual socket bind, traffic, peer identity and live behavior
remain unexecuted and unverified here.

Production root policy is the bounded modern limit of 1000 absolute position
components and maximum speed 10. These are compatibility-prototype bounds,
not recovered world-size or unit facts. Movement stays disabled without the
existing explicit prerequisite booleans. The optional gate/clock/invalid policy
are labeled offline test inputs, not hidden production defaults.

## Input and admission

`ReplacementClientBootstrap.ConfigureInjected` is called once on the creating
Prototype host main thread before tree entry. Its inputs are the absolute JSON path,
explicit offline port factory, minimum-readiness provider, root-motion policy
and optional explicit test clock. Validation precedes all application/factory
acquisition. Relative, UNC, URI, linked, traversal and oversized file inputs
are rejected. The Runtime controlled codec owns the strict versioned JSON
schema and rejects unknown/duplicate fields and malformed values.

The controlled launch includes the explicit original-installation profile,
approved numeric peers/hostnames/galaxy, one nonzero character ID, distinct
connection IDs, phase and overall budgets, disconnect timeout and minimum
readiness assertion. It contains no credentials. Movement is admitted only
when all explicit movement prerequisites are true. Endpoint approval is passed
to the application; the same exact character ID is passed to the host.
Changing the approved selection requires a new composition, not a retry.

The minimum-readiness flag is an operator scenario assertion. It does not prove
complete procedural terrain, validated floor contact or server authority.
The injected92 provider remains responsible for its actual completion task.
The standalone minimum callback verifies the approved scene object matches the
actually selected session and active generation. Under the owned cancellation
token and application resolver it resolves original terrain bytes, decodes PTAT
and compares version/data/generator with the supplied decoded original input.
Its receipt retains only terrain size/hash. This proves bounded original PTAT
admission, not full procedural evaluation, floor contact or authority.

## Attempt and ownership

Production time comes from `Stopwatch`; the fake clock exists only as an
explicit injected test argument. The actual Login button starts the single
attempt. Host observations use actual session phase, submitted client-ready,
received server-ready and published player. Deadlines are checked before
application ticks and before stage transitions can reset the phase timer.
There is no reconnect. An unapproved character is rejected before selection,
zone acquisition or generation mutation even when its template is supported.

A typed stop requests legal disconnect where the actual session permits it,
then retires owned work. Attempt deadlines never force disposal or replace
real cleanup completion. The bootstrap awaits the exact host `Completion`;
startup failures await the exact `RollbackCompletion`. Successful finalization,
startup rejection, rollback fault, run fault and cleanup fault remain distinct states.
`RunFault` preserves faulted operation completion when protocol/send work failed
but local ownership finalized with no cleanup failures. `CleanupFault` requires
actual cleanup failures; it is not inferred from operation task failure alone.
Faulted tasks are observed and the bootstrap's completion also faults for
cleanup failure. Only type names and typed state are exposed in status.

The injecting owner must retain native nodes and keep prototype host's owner context
running until bootstrap completion, then free or quit. A window-close request
starts retirement and does not shorten pending startup rollback. The bootstrap
does not automatically quit an injected92 owner's tree. The standalone owner
awaits actual host or rollback completion, attempts its receipt, then requests
tree quit. Normal success exits 0; startup/run/cleanup/diagnostic failure exits 1.
It never force-quits to satisfy a budget. Immediate forced native
destruction and process termination have no clean-drain guarantee.
An unexpectedly faulted host-finalizer task without actual application/host
finalization leaves the standalone owner pending; it cannot write a completion
receipt or quit while live borrowers remain. This defensive branch is inspected,
not a successful forced-destruction proof.

## Redacted attempt receipt

Version1 `ReplacementClientAttemptReceipt` contains typed outcome, unconditional
synthetic labeling for the offline seam, relative monotonic attempt/stage times
and stop reason, a run-local `selected-1` alias, actual ready/publication/root/
deferred counts and SHA-256 input/resource identities. It preserves typed failure
and cleanup observations, actual host operation-task success, application local
drain/finalization and startup rollback completion/success separately. Failed
construction has no exposed application and may have no resource hashes;
completed rollback is recorded separately from application finalization.

No credentials, token/account/character names, endpoint/address/object IDs,
physical input paths, raw packets/server errors or stack traces are serialized.
Resource hashes are limited to 256, cleanup type observations to 16, strictly
monotonic stage transitions to nine, and output to 65,536 UTF-8 bytes. The
destination is rechecked after observed ownership completion and exclusively
created with `FileMode.CreateNew`; an existing destination is never overwritten.

`DiagnosticState` and `DiagnosticFailureType` distinguish a failed write from
`RunFault` or `CleanupFault`. A write failure preserves the run/cleanup outcome,
faults bootstrap completion and exits 1; it cannot fabricate a successful receipt.
The final typed log reports diagnostic state and actual local-drain completion.
Receipts prove local observations only, never server-observed release or truth.

## Evidence and limits

The Round92 harness (external historical reference) constructs this
production composition against independently authored protected offline peers
and the explicit installed human asset closure. It exercises a supported second
human with the wrong ID, phase/overall stalls, cancellation, window close,
retained-node removal, provider/send failures and delayed startup rollback.
Exact borrowed Runtime inputs are privately staged and separately hashed;
no cross-role source is promoted by the Rendering worker.

These are modern implementation observations, not recovered legacy behavior.
Native controls and injected key events do not prove physical OS input.
Headless verification does not establish GPU rendering or live compatibility.
The separately requested offline GPU success case validates original publication
and saves a native frame before actual drain/quit, with the same receipt/wire/
resource assertions. It adds no live or physical-input evidence.
The Round93 harness (external historical reference) uses the same opt-in
admission/composition with explicit spy ports. It checks rejection before any
acquisition, a supported wrong character, missing movement approval, budgets,
delayed rollback, RunFault/cleanup distinction, an output collision and actual
standalone exit after drain. The unchanged injected92 success path is replayed.
No worker seal or historical private vectors are launcher dependencies.

Stopping condition: seal the offline admission/receipt/cleanup proof. Lead then
assesses operator-approved server/account/one supported character and measured
baseline/resource/minimum/floor/state inputs before requesting specific live
authorization. General terrain/gameplay/avatar and live interoperability remain
open; no cosmetic follow-on round is justified by those missing prerequisites.
